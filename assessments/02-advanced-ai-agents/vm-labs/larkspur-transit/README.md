# Larkspur Transit — MCP Server and Client VM Lab

Module 2 (Advanced AI Agents), **Class 3 — MCP: theory, plus building a server and a client**.

The learner writes a **real MCP server** and a **real MCP client** with the official Python `mcp`
SDK, then drives the server's tools through an agent loop. The checks speak MCP: four of the five
connect their own `ClientSession` to the learner's `server.py` over stdio and exercise the
protocol, so nothing is graded by reading the file.

- **Max Score 50** = 5 checks × 10 points.
- **Target image:** "systemd Ubuntu" (really Ubuntu 25.04, Python 3.13.3).
- **Project directory:** `/home/user/larkspur-transit/`.
- **Service:** `opsd.py` on `127.0.0.1:8757`, installed at `/opt/larkspur-svc` (`root:root 0700`).

## What the learner builds

`server.py`

- three MCP tools — `list_tables`, `get_table_schema(table_name)`, `execute_sql(query)` — each
  described, each with the right required parameters, all exposing the provided SQL functions;
- one MCP resource at `transit://overview` returning a live overview of the database;
- one MCP prompt named `transit_analyst(question)` returning a message sequence;
- a stdio entry point.

`solution.py`

- `TransitMCPClient` — an async context-manager client that spawns `server.py`, initialises the
  session, and relays `tools/list`, `tools/call`, `resources/read`, `prompts/list`, `prompts/get`;
- `mcp_tools_to_openai(mcp_tools)` — MCP tool schemas to the OpenAI `tools=[...]` shape;
- `async run_agent_loop(question)` — the ReAct loop, bounded by `MAX_MODEL_TURNS` (≤ 8).

## The five checks

- **TC01** — a real `initialize` + `tools/list` over stdio advertises the three tools, each
  described and each declaring the right required parameters.
- **TC02** — `tools/call` does real database work against a database the learner has never seen
  (the checks point the server at their own seeded copy through `LARKSPUR_DB`), and both guards
  hold: an unpublished table name and a `DELETE` are refused without executing and without
  dropping the session.
- **TC03** — `resources/list` advertises `transit://overview`, and `resources/read` returns row
  counts that match the live database.
- **TC04** — `prompts/list` advertises `transit_analyst` with its `question` argument, and
  `prompts/get` returns messages carrying a value chosen at grade time.
- **TC05** — `run_agent_loop` returns the answer the oracle computes from SQLite; the service trace
  proves the tool schemas converted correctly, the four tool calls happened in order, each result
  came back keyed to the call that asked for it, and the loop stopped inside its turn ceiling. The
  database access log proves every tool ran in the *server* process, so a client that skips MCP and
  calls the SQL functions itself fails here even though its answer is right. The same interpreter
  start also calls `mcp_tools_to_openai` directly, checks `MAX_MODEL_TURNS` is a whole number in
  1..8, and drives `TransitMCPClient` through the rest of its documented surface, so no method the
  contract names is left ungraded. That last part is scoped to **relay** only: the resource's counts
  and the prompt's interpolation belong to TC03 and TC04, and asserting them here as well made one
  server mistake cost two themes.

**Partial credit is a prefix.** `main.sh` breaks at the first failing case, so a solution that fails
TC01 scores 0, not 40. Measured portal scores are in `VALIDATION.md`; the 40/50 rows in the sweep
are `run-all.sh` running all five checks regardless, which is what shows each defect losing only its
own theme.

## Working on the pack

```bash
./gen_tests.sh                       # regenerate the five checks from one preamble
./build.sh                           # expand the setup template, run every guard, stage the zips

# grade one candidate
PY=<venv>/bin/python ./test-cases/scripts/run-all.sh
PY=<venv>/bin/python SERVER=reference-solution/alt2_server.py \
   SOLUTION=reference-solution/alt2_solution.py ./test-cases/scripts/run-all.sh

# grade every candidate, each on its own port and lab directory
PY=<venv>/bin/python ./sweep.sh

# the ordering matrix
PY=<venv>/bin/python ./validation/permutations.sh
```

A local venv needs exactly what the VM gets:

```bash
python3.13 -m venv /tmp/lkvenv
/tmp/lkvenv/bin/python -m pip install --only-binary=:all: \
    "mcp==1.9.4" "pydantic-settings==2.14.0" "openai==3.1.0"
```

**`mcp` must stay below 2.0.** `mcp` 2.0.0 removed the `mcp.server.fastmcp` module the whole lab is
built on; `build.sh` refuses to ship a setup script whose fallback rung does not constrain it.

## Guards `build.sh` enforces

- at most five test scripts, each syntactically valid;
- every check carries `SVC_WAIT`, `RUN_BUDGET`, `CURL_MAX`, `DEPS_WAIT`, a `report()` +
  `trap on_exit EXIT` single-verdict guarantee, a `chown -R user:user` gated on `id -u user`, a
  `kill_stray_servers` sweep and `PYTHONDONTWRITEBYTECODE`;
- every check carries `trap - ERR`, `set +eE` and `exec 2>>`, the three lines that keep the
  platform's ERR trap and a stray stderr line from voiding the verdict;
- every check carries `stage_project` (grading runs against a copy, never in the learner's project)
  and `run_evidence` (a verdict never names a log file that turned out to be empty);
- the setup script pins all three packages, bounds every package in its fallback rung, and installs
  `curl` and `jq` in the foreground;
- **no apostrophe and no backtick inside any `<<'PY' … PY` body** — the heredoc sits inside `$( )`,
  where an apostrophe unbalances the script and a backtick is silently substituted away by the
  outer heredoc in `gen_tests.sh`;
- the five checks share a byte-identical preamble;
- `problem-statement.md` has no markdown tables, no em dashes, no "How you are graded" section and
  no leaked check structure, has all its sections, and has six task blocks;
- nothing learner-visible names the teaching context or the checks' internals;
- both zips carry `scripts/` **and** `data/` at the root.
